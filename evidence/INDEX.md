Baseline notes (imported 20 Oct from `RISCV_Three_Stage.zip`, byte-identical, `modules/` untouched):
- Only the xor program's `imem.hex` is present; no RISC-V compiler on the importing machine, so addition/sort/negative were not rebuilt.
- `modules/tb_pipeline.v` differs from the version the blueprint audited (143 vs 129 lines): it stops at PC 0x44 (xor-specific) and prints a computed time, not `$time`. Use `simulation/tb_baseline_probe.v` for cycle evidence.
- After reset the baseline executes its first instruction twice (`addi sp,sp,-32` lands in `sp` at two consecutive cycles), so its stack sits 0x20 below the architectural value of F8 (stores at `0xFFFFFFDC`.. instead of `0xFFFFFFFC`..). `tb_ooo_system` therefore compares store data, byte lanes and address pattern with one constant address offset.
- The baseline `exception` output pulses once per loop pass: the squashed fetch after `ret` reads 0x00000000 and IF_ID flags it illegal without checking the squash (F10). Our core must raise `exception` only for a dispatched illegal instruction (D12).
- **Three baseline bugs** (found 23 Oct with `tb_baseline_counters`; `modules/` stays untouched, fixed only in the `pipe_m` copy, D24): (1) after a taken branch the squash of register writes (`wb_stall`) is one cycle early: the branch's own write (JAL/JALR link) is dropped and the **second** wrong-path instruction still writes its `rd` (`ooo_tests/programs/base_rv32i.s`: the `xor a0` behind the loop's `bnez` zeroes the running sum, result 0x32B3 instead of 0x4082); (2) `lb/lh/lbu/lhu` select the byte/halfword with `dmem_read_address[1:0]`, the address of the instruction **now in EX**, not the load's registered offset; (3) `inst_fetch_pc` (`wb.v`) is held during `wb_stall`, so the first two instructions at a taken-branch target get a stale pc (a branch there jumps to a wrong target; `top_mmio`'s `bge` at 0xCC went to 0x120). Stores are squashed correctly (`mem_write && !branch_stall`). `-O0` C code reloads every variable from the stack and rarely puts a branch at a jump target, which is why the course programs pass.
- **Fourth baseline bug** (found 26 Oct with the real `rv32m_d8` C workload; fixed only in `baseline_m/execute_m.v`): `SR` is written `arithsubtype ? $signed(a) >>> b : a >> b`. Inside `?:` next to the unsigned SRL operand Verilog evaluates `>>>` unsigned, so **every SRA/SRAI is a logical shift** (`srai t0,t0,31` on 0xFFFEFFFD gave 1, not 0xFFFFFFFF; gcc emits it to sign-extend for `mulh`, so `pipe_m` returned 0x7D instead of 0x7F). `pipe_m` now computes SRA on its own wire and masks every shift amount to [4:0] (F5).
- `pipe_m` `exception` now follows D12 like the OoO core: set only by an illegal instruction that really executes (`ex_real`) or a misaligned fetch, sticky until reset. Before, it copied the baseline ID-stage pulse (F10), so it read 1 on correct programs whenever the zero words behind the final `for (;;)` were decoded; `tb_baseline_counters` now checks `exception` for `pipe_m` as well as `pipe_ooo`.
